# Version 1.4: alineación con backend actualizado

Esta migración sigue V1.3 y alinea Cloud SQL con las entidades desplegadas tras
el pull de `main`:

- `Usuarios`: nombres, longitudes, nulabilidad y enums que espera `User`; admite
  cuentas anonimizadas/bloqueadas y actualiza `USER` heredado a `USUARIO`.
- `idempotencia_reportes`: dos índices únicos para llave y UUID de cliente,
  UUIDs `VARCHAR(36)`, hash SHA-256 hexadecimal `VARCHAR(64)` y referencia al reporte con
  `ON DELETE SET NULL`. La reserva persiste cuando HU-05 elimina el reporte.
- `Bitacora_Administrativa`: admite acciones de autor/sistema sin administrador
  y queda enlazada a reportes mediante `ID_Reporte`.
- Índices `idx_reportes_usuario_fecha` e `idx_bitacora_reporte_fecha` conforme
  al contrato y nombres declarados por el backend.

## Prevalidación requerida

El backend del repositorio usa `spring.jpa.hibernate.ddl-auto=update`; puede
haber creado ya columnas, tablas o índices fuera de estas migraciones. Antes de
aplicar V1.4, consulta el esquema real y no ejecutes de nuevo los DDL que ya
existan:

```sql
SHOW CREATE TABLE Usuarios;
SHOW CREATE TABLE Bitacora_Administrativa;
SHOW CREATE TABLE reportes;
SHOW TABLES LIKE 'idempotencia_reportes';

SELECT index_name, non_unique,
       GROUP_CONCAT(column_name ORDER BY seq_in_index) AS columnas
FROM information_schema.statistics
WHERE table_schema = DATABASE()
  AND table_name IN ('reportes', 'Bitacora_Administrativa')
GROUP BY index_name, non_unique;
```

La migración V1.4 automatiza el caso secuencial V1.0-V1.3. Si el esquema fue
creado por Hibernate o tiene solo parte de esos cambios, prepara y revisa un
DDL específico contra el resultado de la inspección; no la ejecutes a ciegas en
Cloud SQL. Confirma además que `Registros`, `Fotos` y `Bitacora_Administrativa`
cumplieron la precondición de V1.3 antes de haberla aplicado.

## Comprobación posterior

Las dos filas de unicidad de `idempotencia_reportes` deben ser `non_unique=0`.
`idx_reportes_usuario_fecha` debe listar exactamente
`ID_Usuario, Fecha_Evento, ID_Reporte`, en ese orden. `SHOW CREATE TABLE` debe
mostrar `ON DELETE SET NULL` en la FK de idempotencia y en la de bitácora.

El frontend actualizado aún declara su outbox como almacenamiento temporal
JSON; esta migración no representa SQLite móvil ni cifra dicho archivo. Ese
almacenamiento debe cambiarse en el frontend para que exista persistencia local
cifrada; queda fuera del alcance SQL de V1.4.

`U1.4` es únicamente para bases desechables. No se puede revertir sin pérdida
si hay reservas de idempotencia, usuarios anonimizados, correos mayores de 50
caracteres, nombres nulos o acciones de bitácora sin administrador.
